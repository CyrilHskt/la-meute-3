# Where each certification competency is demonstrated

A reading key for this repository. Competency wording is quoted verbatim from
the official RS6515 record ([France Compétences,
RS6515](https://www.francecompetences.fr/recherche/rs/6515/)) — *Développer une
application décentralisée avec les technologies blockchain*.

## C1 — « Rédiger un cahier des charges en décrivant les objectifs, les modalités de réalisation et les fonctionnalités d'une future application décentralisée »

The specification is delivered as a separate document. It defines the actors
and their states, the state machine, the governance rules section by section
(§7.0 to §7.6bis), the parameters, and the limitations accepted up front.

`contracts/Meute.sol` cites its section numbers directly from NatSpec, so code
and specification can be read side by side.

## C2 — « Développer un contrat intelligent (smart contract) en utilisant un langage de programmation adapté à une technologie blockchain »

**`contracts/Meute.sol`** — 772 lines, Solidity 0.8.28, pinned rather than
floating (`0.8.28`, not `^0.8.28`) so the build is reproducible and the
deployed bytecode verifiable.

One contract holds both the membership registry and the governance mechanics.
The two-contract alternative and why it was rejected are in
[recap-conception.md §9](recap-conception.md). No owner, no pause, no upgrade
path after deployment.

Notable mechanics: passive dormancy, a quorum denominator frozen at proposal
opening, one voting cycle shared by four proposal types, and a three-outcome
confirmation vote whose default is the outcome that harms nobody.

## C3 — « Exploiter un jeton numérique (fongible ou non) en utilisant les librairies et les standards pratiqués dans l'industrie »

**Standard: ERC-721** (non-fungible), implemented on **OpenZeppelin 5.6** —
`ERC721`, plus `ReentrancyGuard`, `EnumerableSet`, `Base64` and `Strings` from
the same library. The industry standard is used as-is rather than
reimplemented; what the project adds is constrained through the library's own
extension points.

**Non-transferability** is enforced by overriding `_update`, the hook every
ownership change passes through in OpenZeppelin 5.x — not `transferFrom`, which
would leave `safeTransferFrom` and future paths open. The guard allows mint
(`from == 0`) and burn (`to == 0`) while blocking holder-to-holder transfer.
The pitfall this avoids — blocking the hook outright and making the contract
inert on deployment — is documented in
[recap-conception.md §8](recap-conception.md).

**Token identity**: the token id is the holder's address reinterpreted as an
integer, so `ownerOf` and `balanceOf` answer every membership question without
a counter or a secondary mapping.

**Metadata**: `tokenURI` returns a fully on-chain data URI — JSON and SVG
generated by the contract and Base64-encoded via OpenZeppelin's `Base64`, with
no server and no IPFS pin.

Why a token at all, and why non-transferable, is in
[recap-conception.md §2](recap-conception.md): the card *is* the registry, and
a transferable membership card would make voting rights tradable.

## C4 — « Identifier les points d'attention en matière de sécurité et les optimisations adaptées en analysant les fonctionnalités d'un contrat intelligent »

### Security

**[security.md](security.md)** — the threat model class by class: reentrancy,
DoS by gas limit, DoS by unexpected revert, force feeding, front-running,
timestamp manipulation, arithmetic, plus the web layer's own surfaces.

Reentrancy is demonstrated, not asserted:
`contracts/test/ReentrantExpenseBeneficiary.sol` is a real attacking contract
that attempts re-entry from its `receive()`, and the suite asserts it fails.
`contracts/test/RejectEther.sol` covers the recipient-refuses-payment case.

Limitations are stated explicitly rather than omitted — in particular that the
unbounded-loop risk is *mitigated* by `pruneDormant`, not eliminated.

### Optimisations

| Optimisation | Where | What it saves |
|---|---|---|
| Storage packing | `struct Card` | `Rank` (8 bits) + `lastActivity` (40) + `postponements` (8) = 56 bits, one slot instead of three — one `SSTORE` per card update rather than three |
| One field, two meanings | `lastActivity` | Tracks probation for a Cub and dormancy for a Wolf. Mutually exclusive states, so a second field would always be dead |
| Custom errors | 22 declarations | A 4-byte selector instead of a revert string stored in bytecode — and the EIP-170 24 KB limit is tight because the SVG ships on-chain |
| `immutable` fee | `fee` | Set once in the constructor, then read from bytecode rather than storage |
| No on-chain loop over donors | `totalDonations` | `O(1)` per address; the leaderboard is built off-chain from events, because the donor set is unbounded unlike the pack |
| Permissionless pruning | `pruneDormant` | Lets anyone bound the cost of the `activeWolves` loop without any privileged role |
| Widen before multiplying | `_quorumReached` | `uint256` casts prevent a `uint32` overflow that would revert and make a proposal permanently unexecutable |
| Author kept in the event | `ProposalOpened` | One address per proposal stays out of storage; the indexer rebuilds the author table from logs |
| Multicall batching | `scripts/sync-dao.js` | Every card read, proposal read and singleton read batched into one `aggregate3` call instead of one `eth_call` per item — this per-item cost, repeated every 30 minutes, was what exhausted the RPC quota |
| Snapshot instead of live reads | front | Config values (`fee`, `DORMANCY_DELAY`, `MAX_POSTPONEMENTS`, `VOTE_DURATION`) come from the published snapshot rather than an RPC call on every page mount, for every visitor |

## C5 — « Mettre en place la gestion des versions en utilisant des méthodes d'intégration continue »

Two independent version tracks, because a CSS change has no reason to bump a
contract version:

| Workflow | Role |
|---|---|
| `ci.yml` | On every push and pull request: compile, ABI-drift check, TypeScript typecheck, 73 contract tests; then front build, function typecheck and 26 function tests |
| `version-check.yml` | On a `contract-v*` tag: cross-checks the tag against the `VERSION` constant compiled into the contract |
| `release-contract.yml` | Manual: bumps `VERSION` in `Meute.sol`, commits, tags `contract-vX.Y.Z` |
| `release-front.yml` | Manual: bumps `front/package.json`, commits, tags `front-vA.B.C` |
| `sync-dao.yml` | Every 30 minutes: runs the indexer against the production chain |

`scripts/check-contract-sync.js` runs in CI and compares the front's committed
ABI against the freshly compiled contract, and the committed version against
the Solidity `VERSION` constant — so the front cannot silently drift from the
contract it talks to.

## C6 — « Vérifier la résilience d'une application décentralisée, en mettant en place des tests fonctionnels »

**`test/Meute.ts`** — 73 tests, TypeScript, `npx hardhat test`.

They are end-to-end functional scenarios rather than unit tests, because what
is worth proving involves time and several accounts: a 90-day probation, a
180-day dormancy, a quorum that shifts as members fall dormant. Time
advancement uses `networkHelpers`, so those delays are exercised rather than
assumed.

Resilience specifically: the suite covers an attacking contract attempting
reentrancy, a beneficiary refusing payment, a member resigning between a
proposal opening and its execution, a fully dormant pack, and a vote reaching
its deadline with nobody having voted.

`contracts/test/` holds helper contracts used *by* these tests, not `*.t.sol`
unit tests.

The web layer has its own suite — 26 tests, `npm run test:functions` in
`front/` — covering the signed-token logic and the server-side derivation of a
proposal's author.

## C7 — « Développer un code informatique en utilisant un langage de programmation adapté aux technologies web »

**`front/`** — Vue 3, Vite, TypeScript, `viem`.

Writes always go through the connected wallet; no backend holds a privileged
path to the contract. Reads come from a snapshot maintained by an indexer, so
no visitor scans the chain themselves — the reasoning, and the free-RPC limits
that forced it, are in [architecture.md](architecture.md).

Server-side code is TypeScript too: Netlify Functions handle members-only
reads, the Discord OAuth2 flow and the immediate snapshot patch after a
transaction.

Also included: French/English localisation, an explicit dark mode, and a local
demo mode (`npm run demo`) replaying scripted governance scenarios against a
Hardhat node with time travel.

## C8 — « Déployer un contrat intelligent (smart contract) sur une blockchain »

Deployed with Hardhat Ignition. Deployment journals for both chains are
committed under `ignition/deployments/`.

| Chain | Id | Address | Role |
|---|---|---|---|
| Base Sepolia | 84532 | `0x71D5E89D8295B933c140332fa056609A8dad2218` | Production since 2026-08-03 |
| Sepolia | 11155111 | `0x528d68AFE81572c26f213de4Aa3e9B94578bDa3E` | Original L1 deployment, kept as rollback |

The current source compiles to exactly the bytecode deployed on both chains —
the metadata hash embedded in the deployed bytecode matches a fresh local
compile, which is what makes source verification meaningful rather than
decorative.

The move from L1 Sepolia to the Base L2 was a cost decision taken on measured
figures. The front, the Netlify functions and the indexer all select their
chain from configuration, so a rollback is an environment variable rather than
a code change.
